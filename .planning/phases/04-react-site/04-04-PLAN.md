  <how-to-verify>
    1. **Start the dev server.**
       Run: `cd site && npm run dev`
       Open the URL printed in the terminal (typically http://localhost:5173) in a desktop browser.

    2. **DSGN-01 (aesthetic) — desktop full-width view.**
       Look at the page at >=1280px viewport width.
       Expected: warm-white background (stone-50), sticky filter bar with stone-100 background, 5-column masonry of thumbnails with small gaps, hover any thumbnail to see the photographer-name badge fade in at the bottom-inline-end corner. Active filter chips should fill with the warm-gold accent color when clicked.
       Confirm: looks subtle/modern/clean — no jarring colors, no cluttered UI, no broken spacing.

    3. **I18N-01 (Hebrew text audit).**
       Visually scan every visible UI string. Expected Hebrew strings:
       - Page title (browser tab): "האלבום שלנו"
       - Filter chips: 3 photographer names (עביר סולטן, ענבל זלדין, Magnate Images — last is a proper noun so English is OK), 5 phase labels (הכנות, צילומים, ארוחה, חופה, ריקודים)
       - Section headers: same 5 phase labels with `(N תמונות)` count suffix
       - Hover badges: photographer real names from PHOTOGRAPHER_NAMES
       - Clear all button (when filters active): "הצג הכל"
       Confirm: no English UI strings appear except the proper noun "Magnate Images".

    4. **I18N-02 (RTL layout audit).**
       Open browser devtools → Elements panel. Find the `<html>` tag. Confirm it has `lang="he"` and `dir="rtl"` attributes.
       Visually verify:
       - Filter chips flow right-to-left (first chip on the right edge of the bar)
       - Section headers are right-aligned (Hebrew text starts on the right)
       - The photo count `(N תמונות)` appears to the left of the section title (because in RTL, ms-2 puts margin on the visual left)
       - Hover badge appears in the bottom-LEFT corner of thumbnails (because `end-0` in RTL = visually left)
       Confirm: no element is clipped, no text overlaps another, no padding on the wrong side.

    5. **GALL-02 (responsive masonry).**
       Open devtools → Toggle device toolbar (responsive mode).
       Test these viewport widths:
       - 375px (mobile): expect 2 columns
       - 768px (tablet): expect 3 columns
       - 1280px (desktop): expect 5 columns
       Switch between widths and confirm the layout reflows without jank.

    6. **GALL-04 (lightbox navigates filtered set only).**
       Back at desktop width, click a photographer chip (e.g., עביר סולטן) to filter — now only that photographer's photos are visible (should be 5 photos across various sections).
       Click any visible thumbnail to open the lightbox.
       Press the right arrow key (or click the next arrow) repeatedly. The lightbox should cycle through ONLY the 5 filtered photos, not all 15. After the last one, it should either loop back to the first or stop — but it must NOT show a photo from a different photographer.
       Press Escape to close.
       Click another chip combination (e.g., add a phase filter — חופה) — now only the intersection is visible (1–2 photos). Open the lightbox on one of them; prev/next should only navigate within that 1–2 photo subset.
       Click "הצג הכל" to clear filters. Confirm all 15 photos return.

    7. **FILT-04 (face filter absent from DOM).**
       In devtools Elements panel, search the DOM for any element matching `[data-testid="face-filter"]` or any UI that looks like a face/people filter. Since the fixture has `people: []`, there should be ZERO such elements in the DOM.
       Confirm: no face filter element exists (not just hidden — fully absent).

    8. **Console errors check.**
       Open devtools → Console tab. Reload the page. Interact with all filter chips and open/close the lightbox a few times. Expected: zero red errors. Yellow warnings from third-party libraries (React DevTools tip, Vite HMR messages) are acceptable.

    9. **Build smoke test (optional but recommended).**
       Stop the dev server (Ctrl+C). Run: `cd site && npm run build && npm run preview`
       Open the preview URL. Repeat steps 2–8 against the production build to ensure nothing breaks in the bundled output.

    If ANY check fails, describe the specific failure (which step, what you saw vs expected). The orchestrator will route the failure into a gap-closure plan.
  </how-to-verify>
